本文记录 M4 的范围、决策和实现顺序。规格以这些文档为准，本文只做索引：

## 现状（M3.5 结束时）

| 位置 | 状态 |
|---|---|
| crhs Web API | `privileged = true` 直接 400（`task-routes.ts`）；MCP / agent 工具不暴露 `privileged` |
| crhs 任务 | `tasks.attempt`、`tasks.privileged` 已有；`authorization_*` 按最终失败处理，没有 `awaiting_authorization` |
| crha 非特权模式 | `privileged = true` 一律 `privileged_unsupported`；`[privileged] mode` 只在 `Hello` 中上报 |
| crha 特权模式 | `client/internal/privileged` 为空；`crha privileged run`、`grant`、`pending`、`approve` 只有命令行骨架 |
| 协议 | 1.0；`TaskStart` 已带 `attempt` 与 `authorizations: [bytes]` |
| 数据 | 没有 `authorizations`、`user_credentials`、`nodes.trust_*` |
| 文件安全 | 现有 `file.*` 用 `Lstat` / `O_NOFOLLOW`，只检查最后一级 |
| 测试环境 | 方法见 [testing/privileged.md](testing/privileged.md)（当时只有说明） |

## 需求与完成标志

1. crha 节点的四种处理方式：`forward` / `native` / `ignore` / `reject`。
2. crha 特权模式：信任配置、授权校验、一次性授权、本地批准、本地日志。
3. crhs：信任缓存、授权方案计算、授权签名、`awaiting_authorization`、授权重试；规则的 `privileged` 维度。
4. 用户授权：`crha grant`（SSHSIG）、WebUI Passkey、`crha approve`、联署；任务组一次签名覆盖多个节点。
5. SSH 节点忽略特权并提示，SFTP `file.*` 保持可用。
6. WebUI：信任摘要、导出 trust 片段、授权等待页、凭据管理、授权页。

**完成标志**：同一节点分别配置为"信任服务端"和"只信任用户"，两条路径都能跑通，且"只信任用户"时
crhs 无法单独提权（有专门的测试）；SSH 忽略特权且不破坏 file 任务。

**不在 M4**：`crha upgrade --apply`（移到 M6）；crhs 通过外部 ssh-agent 签名（可选项目）；`run0`
只作为实验性后端，不列入验收；`crha grant --submit`。

## 决策摘要

| 主题 | 结论 | 规格 |
|---|---|---|
| 工具暴露 | MCP / agent 暴露 `privileged`；规则增加 `privileged` 维度，Ask 下特权任务总是先审批（D86） | access-control.md |
| native | `sudo -n` / `doas -n` 拉起 `crha privileged stdio` helper，exec 和 `file.*` 都走它（D87） | privilege.md "非特权模式如何处理特权任务" |
| 授权对象 | 定长数组；`task_ids` 列表；SSHSIG message 是 payload 原文；WebAuthn ES256 / EdDSA / RS256（D88） | protocol.md "授权对象" |
| `spec_sha256` | `SHA-256(CBOR(TaskSpec))` | 同上 |
| 任务组 | 一个签名覆盖多个节点，已用列表键为 `(授权 id, 任务 id)`；部分被拒只为被拒节点重签（D88） | privilege.md "授权" |
| 本地批准 | 只用于单任务；`local.request` / `local.decision` / `local.withdraw`，不占用 `task.start`；crhs 签名被拒后可回退到 local（`attempt + 1`）；任务组没有其他路径时直接失败（D89） | privilege.md "本地批准"、"预演与 fallback" |
| 信任缓存 | crha 只推送 `trust.summary`；转发授权拒绝前先刷新（D90；吊销部分被 D103 移除） | protocol.md "新增命令和事件" |
| 错误码 | 规则/路径拒绝属于可重试的 `authorization_rejected`；新增终态 `privileged_unavailable` | protocol.md "task.start" |
| crh-priv | 复用帧和命令/事件抽象，无 Noise，4 字节长度前缀，`role` 与 `SO_PEERCRED` 对应；断开时特权任务继续运行 | protocol.md "crh-priv" |
| 签名实现 | crhs：`node:crypto` + 手写 SSHSIG；`crha grant`：`ssh-keygen -Y sign`；crha：`x/crypto/ssh` + 手写 SSHSIG codec、手写 WebAuthn 验证；crhs WebAuthn：`@simplewebauthn/server@14` / `browser@14`（D91） | privilege.md "签名方式" |
| RE2 | Node 包 `re2`（预构建覆盖 linux x64/arm64 glibc/musl、Node 22/24/26）；公共子集；crhs 编译失败保守处理 | privilege.md "防护规则" |
| 文件路径 | `openat2(RESOLVE_BENEATH \| RESOLVE_NO_SYMLINKS)`，基于 fd 操作，不支持时 fail closed | privilege.md "方法与目标" |

`re2` 落地时：在 `pnpm-workspace.yaml` 放行它的构建脚本；离线环境用 `RE2_DOWNLOAD_MIRROR`；构建失败不得退回 JS 内置 RegExp；M6 打包时附带对应 ABI 的 `re2.node`。

### 仍待实测的事项

生态调查（2026-10-29）只核对了文档和源码，以下必须在原型或 CI 中确认，结论不符时回来修改规格：

1. ~~sudo 的输出与信号~~：已验证（2026-10-29，`crh-m4-proto/sys`，Ubuntu 24.04 容器，sudo 1.9.15p5）。没有控制终端时 `use_pty` 不生效，helper 看到三条独立的 pipe；sudo fork 出目标进程，SIGTERM 会被转发，SIGKILL 发给 sudo 后 root 进程成为孤儿；crha 直接 kill root 进程得到 `EPERM`；需要密码时 `sudo -n` 退出码 1、`sudo: a password is required`。
2. ~~opendoas~~：已验证（opendoas 6.8.2，PAM 版本）。与调查报告不同，它**不** exec 替换自身，而是 fork（`pamauth()`），信号行为与 sudo 相同；不在允许列表的命令 `doas -n` 退出码 1、`doas: Operation not permitted`。
3. ~~`openat2`~~：已验证（宿主内核 7.2，rootless podman 默认 seccomp）。`openat2` 可用；`RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS` 下中间级和末级符号链接都返回 `ELOOP`。rename 竞态用例留到 M4.1 的执行器测试。
4. ~~`re2@1.27.0` 的安装与语法差异~~：已验证（2026-10-29，`crh-m4-proto/re2`）。pnpm 12 不放行时报 `ERR_PNPM_IGNORED_BUILDS`；`pnpm-workspace.yaml` 中 `allowBuilds: { re2: true }` 后下载预构建的 `linux-x64-147.br`。34 个模式、440 组输入中只有两处差异，都是 re2 能编译、Go 拒绝：`\C`（按字节匹配）和 `\p{Script=…}`；两边都能编译的模式匹配结果完全一致，`u` 标志无影响。公共子集：不用 `\C`、`\p{Script=…}`（用 `\p{Latin}`）、环视、反向引用、`\Z`、`\h`，计数不超过 1000。
5. ~~SSHSIG 三方互验~~：已验证（测试向量由 TS 参考实现生成，Go 与 `ssh-keygen -Y verify` 交叉校验，含 `sk-ssh-ed25519` 和 `sk-ecdsa` 向量；`ssh-keygen` 接受缺 UP 的 sk 签名，crha 更严格）。真实 FIDO 硬件 key 签名未实测。
6. WebAuthn 实机：iCloud Keychain、Google Password Manager、1Password、Windows Hello、FIDO 硬件 key 实际使用的 COSE 算法。
7. （可选）run0 在 Arch systemd 262 上的 `--pipe`、退出码、取消和 polkit 最小权限配置。

## 架构

```
crhs 策略（含 privileged 维度）/ Auto Review
        │
        ├── SSH 节点：ignore，加输出提示
        │
        └── crha 节点（Hello.privileged_mode）
              ├── ignore：非特权模式自身身份执行
              ├── reject：privileged_unsupported
              ├── native：sudo/doas 拉起 `crha privileged stdio`，crh-priv over stdio，不校验授权
              └── forward
                    │ trust.summary（推送）
                    ▼
                  crhs 从缓存计算授权方案（RE2，只看所有者）
                    ├── crhs execute：签 exact + task_ids + 短 deadline
                    ├── 所有者 user：awaiting_authorization（Passkey / 粘贴 crha grant）
                    ├── local：local.request → 等 local.decision
                    └── 无路径：拒绝并说明
                          │ task.start（attempt）
                          ▼
                  crha 非特权模式 → crh-priv over unix socket（SO_PEERCRED）
                          ▼
                  crha 特权模式：校验 payload/signatures/trust/used → 规则、路径、env、spec hash → 执行
```

## crhs 侧数据

- `authorizations`：一个 payload 一行（`id`、`payload` bytes、`signatures` JSON、`issuer_user_id`、
  `task_ids`、`deadline`）。用户粘贴或 Passkey 签发的授权都存这里，供"查找已有授权"复用。
- `user_credentials`：所有者的 SSH 公钥（指纹）和 WebAuthn 凭据（credential id、COSE 公钥、RP ID）。
  crhs 用 TrustSummary 中的指纹 / credential id 匹配所有者的凭据，确定哪些 user 信任项属于这位所有者。
- `tasks.authorization`（JSON）：方案、payload id、attempt、trust digest、最近一次拒绝原因。
- `nodes.trust_report` / `trust_digest`：最近一次 `trust.summary`（`ok` / `unavailable` / `not_forward`）。
- `secrets.authorization_signing_key`：首次启动生成；`crhs keys export` 已列出这一项。

## 阶段

### M4.0 规格与测试向量

- 规格已写入 protocol.md / privilege.md / access-control.md。
- 已完成：`packages/protocol/src/privileged.ts`（M4 类型的 codec）、`test/interop/m4_vectors.json`、`test/interop/m4_authz_cases.json` 及其 TS 测试（参考 SSHSIG / WebAuthn 验证器、`ssh-keygen -Y verify` 互验）。Go 侧在 M4.1 / M4.2 实现时接入同一批文件。
- golden vector（`test/interop/`）：授权对象、`spec_sha256`、`TrustSummary` digest、crh-priv 握手和帧、
  SSHSIG（Go / Node / `ssh-keygen` 互验，含 `sk-*`）、WebAuthn assertion（ES256 / EdDSA / RS256 正例和反例）。
- 授权判定共享用例（JSON）：规则匹配、prefix / regex、env、别名、`task_ids` / attempt、时间边界、联署、
  crhs 编译失败的保守处理；Go 特权模式校验和 TS 方案计算各跑一遍。
- 上文"仍待实测"的 1–4 项做最小原型。

### M4.1 打通 `privileged`：ignore / reject / native + SSH

- crhs：去掉 400；规则的 `privileged` 维度；MCP / agent 工具暴露 `privileged`；按节点模式分流；
  `awaiting_authorization` 状态和 `attempt + 1` 重试的骨架（此阶段还没有路径会进入它）。
- crha：`ignore`、`reject`；crh-priv 协议的 Go 实现；`crha privileged stdio` 与 `native`。
- 执行器：特权路径的 `openat2`、env 白名单、固定 PATH、cwd `/`。
- SSH：ignore + 输出提示；SFTP `file.*` 不变。
- 任务组：ignore / native 路径直接可用。
- podman fixture 第一版（镜像、entrypoint、sudo / doas）。

**验收**：native（sudo、doas）下 exec 和 file 都能执行，取消和超时由 helper 完成；ignore、reject 行为正确；SSH 忽略并提示。

### M4.2 crha 特权模式（独立可用）

- `privileged.toml` 解析和校验；unix socket + `SO_PEERCRED`；crh-priv 的 `forward` / `local` 角色。
- 授权校验（privilege.md 的 10 步）：SSHSIG、WebAuthn；used 持久化；本地日志。
- `crha privileged run`、`crha pending/approve/deny`。
- `trust.query` / `trust.summary`、`local.*`。

**验收**：不经过 crhs，直接向 socket 发一条签名任务可以执行；重放、过期、错 task id、错 attempt、
符号链接、env、prefix 绕过全部拒绝；本地批准流程可用。

### M4.3 crhs 签名 + 信任缓存 + forward

- 授权签名密钥与 SSHSIG 签名。
- 协议 1.1：`trust.summary`；信任缓存、digest 审计、WebUI 信任摘要和 trust 片段导出。
- 方案计算（`re2`）；crhs execute 路径；crha 拒绝后的 fallback；任务组的 crhs 签名路径。
- 非特权模式 `forward`。

**验收**：信任 crhs execute 的节点能跑特权任务；只信任 user 的节点上 crhs 无法单独提权。

### M4.4 用户控制路径

- `user_credentials`、WebAuthn 注册（`supportedAlgorithmIDs: [-7, -8, -257]`）和签名、授权等待页。
- `crha grant` 与 `POST /api/authorizations`；已有授权的查找和复用。
- 本地批准：`local.request` / `local.decision` / `local.withdraw`，WebUI 提示。
- 联署；任务组的用户签名（一个 payload 覆盖多个节点，部分被拒只重签被拒节点）。
- 授权页：展示授权 payload，只对管理员可见；吊销已由 D103 移除。

**验收**：只信任 user 的节点，crhs 单独执行失败，用户签名后成功；要求联署时缺任一个签名都失败。

### M4.5 收尾

- 时钟偏差警告（`clock_warn`）；trust reload。
- 跑完整测试矩阵，更新 roadmap 进度。
