# 用户、归属与审计

## 用户模型

单组织、多用户。所有表都带 `org_id`，但 v1 只有一个组织，不提供多组织功能。

| 对象 | 说明 |
|---|---|
| User | 登录 WebUI 的人，分为**管理员**和**普通用户**两种。v1 用本地密码 + Passkey 登录 |
| UserGroup | 用户组，由管理员维护，用于分享会话和向一组用户授予节点访问 |
| UserCredential | 用户的签名凭证：SSH 公钥（含 FIDO 硬件 key）、Passkey。用于登录和签发提权授权 |
| ApiToken | 属于某个用户，作为操作者链上的一级，只能收紧；MCP 和自动化使用 |
| Node | 节点，属于组织，由管理员管理，可以属于多个节点组。用户通过访问授权看到并使用它 |
| NodeGroup | 节点组，例如 `web`、`prod`，由管理员在 crhs 中维护。用于选择节点（授权规则、批量执行、计划任务）和授予访问；特权模式的信任别名通常填它的 UUID |
| NodeAccessGrant | 访问授权（node access grant，与 privilege.md 的提权授权是两回事）：管理员授予用户或用户组访问节点或节点组，只有一个级别（查看并执行） |

节点用**节点组**来组织，不另设标签。凡是需要"一组节点"的地方，都写成节点和节点组的列表，例如 `["web-1", "prod"]`。文档和界面里一律写"节点组"或"用户组"，不单独用"组"指代节点组。

节点组由管理员在 crhs 中维护，成员关系立即生效：

- 节点组只包含节点，不支持嵌套。crha 节点和 SSH 节点一样，成员关系都在 crhs 中维护，不再来自 crha 配置；旧版 `crha.toml` 中的 `groups` 已移除，出现时进程启动失败（不静默忽略）。
- 节点组和节点共用一个名字空间：节点不能与节点组同名。
- 节点和节点组都有不可变的 UUID。所有内部引用（授权规则、访问授权、任务组的目标）一律存 UUID，名字只用于输入和显示：API、agent 工具、MCP、CLI 接受名字（以及 UUID），写入时解析成 UUID，显示时取当前名字，引用的对象已删除时显示为"已删除的节点 / 节点组"。
- 因此改名只改一个字段，不改写任何引用；删除后重建同名对象会得到新 UUID，旧引用不会作用到新对象上。
- 名字的规则：正则 `^[A-Za-z][A-Za-z0-9._/-]*[A-Za-z0-9]$`，长度 2–64；以字母开头，以字母或数字结尾，中间可以是字母、数字、`.`、`_`、`/`、`-`。唯一性和查找都按小写比较，显示保留原样。以 `_` 开头的名字保留给系统（正则已排除）；目前只有 `_all`：当前用户（会话、计划任务、token 为其所有者）可访问的所有节点，在使用时求值。
- 生成默认名字（注册令牌的 `name_hint`、主机名、SSH 主机）时先规范化：不允许的字符换成 `-`，补足开头字母和结尾字母或数字，截断到 64；冲突时加 `-2`、`-3` 后缀。

## 用户类型

不设角色和细粒度权限，只有两种用户：

| 类型 | 能做什么 |
|---|---|
| 管理员 | 普通用户的全部能力；管理用户和用户组；模型配置；管理节点、节点组、SSH 凭据和访问授权（创建注册令牌、确认注册、添加 SSH 节点、删除或改名节点、调整节点组成员）；查看所有节点和会话（别人的会话默认只读，不能代替所有者改规则或审批；被显式分享 `chat` 后可以对话；可以管理分享）；查看全部审计 |
| 普通用户 | 管理自己的会话、计划任务、API token；通过访问授权查看和操作节点（直接授予自己或自己所在用户组的节点，以及所授节点组的当前成员）；访问分享给自己的会话；查看与自己相关的审计 |

管理员不能修改自己的类型，也不能停用自己：这两件事由另一名管理员操作，避免把自己锁在外面。

"能对节点做什么"不由权限表决定：用户本人操作时只看"能否访问这个节点"；代表用户行事的会话、计划任务和 API token 还要受自己规则链上的授权规则约束（见下文）。

在只信任用户的节点上，crhs 侧的任何身份都不足以提权，必须由该节点信任数组中的用户本人签名（或在节点上本地批准），见 [privilege.md](privilege.md)。

## 归属、访问授权与分享

节点和节点组属于**组织**，由管理员管理；会话、计划任务和 API token 属于创建它的**用户**：

- 节点属于组织，不属于任何用户：删除 `nodes.owner_user_id`。注册令牌、SSH 节点和 SSH 凭据都由管理员创建，节点注册仍由管理员确认。
- 会话属于创建它的用户；subagent 的子会话、计划任务产生的会话，属于父会话或计划任务的所有者。
- 计划任务和 API token 也属于创建者，但不支持分享。

节点通过**访问授权**（node access grant）向用户开放：一条记录 = 被授权方（用户或用户组）+ 目标（节点或节点组），只有一个访问级别（查看并执行）：

| 被授权方 | 说明 |
|---|---|
| 用户 | 查看节点和 Facts，并在节点上执行任务（包括请求特权任务） |
| 用户组 | 同上，组内成员都获得这条授权 |

按节点组授权时成员关系动态生效：之后加入节点组的节点自动对该被授权方可用。

节点和会话的可见性：

- 一个用户能访问的节点 = 直接授予自己或自己所在用户组的节点，加上所授节点组当前的成员；管理员能访问所有节点。
- 没有访问权限的节点**不可见**：不出现在列表、选择器和规则编辑器中，按 id 访问返回 404（不是 403）。
- 任务和任务组能否查看只取决于用户与任务的关系，与节点访问无关：`on_behalf_of` 用户可以看到自己（以及自己的会话、计划任务、token）发起的任务，即使之后失去了节点的访问权限；会话分享的参与者通过会话看到它发起的任务；管理员可以看到全部。能访问节点并不能看到别人在这个节点上的任务。
- 访问在任务创建时检查，在任务真正下发给节点之前（审批、签名等待之后）再检查一次；失去访问的等待中任务以错误结束（`node_access_revoked`）。已经下发的任务不受影响。
- 用户本人在 WebUI 中操作，仍然只检查能否访问节点。
- 访问授权与提权信任完全独立：它只决定 crhs 是否允许发起；`forward` 节点上的特权任务仍由 crha 的信任配置最终决定（见 [privilege.md](privilege.md)）。在只信任某个用户签名的节点上，被授予访问的其他用户请求特权任务时仍需要那个用户签名或本地批准。

会话可以**分享**给额外的用户或用户组（节点不再分享）：

| 资源 | 访问级别 | 含义 |
|---|---|---|
| 会话 | `view` | 查看会话内容和状态 |
| 会话 | `chat` | 在 `view` 之外，向会话发送消息、打断运行 |

会话的 API 返回服务端每次计算的 `capabilities`（`view`、`chat`、`manageShares`、`configure`）和仅用于展示的 `relationship`（`owner` / `admin` / `shared`）；授权判断只用 capabilities，不再使用有效的 `access` 字段。`shares.access` 仍然表示这条分享授予的级别（`view` / `chat`），不是最终能力。

- 节点、节点组和访问授权只能由管理员管理；会话的分享、取消分享、删除只能由所有者（或管理员）操作。
- 分享根会话也覆盖它下面的 subagent 子会话；子会话也可以单独分享。继承来的 `view` / `chat` 取链上最强的一级。撤销分享会关闭该会话（或覆盖它的根会话）上已经建立的事件流。
- **会话以所有者的身份行事**：被分享了 `chat` 的用户向会话发消息时，能访问的节点是所有者**当前**的访问范围，规则是这个会话自己的。分享会话等于让对方在所有者授予会话的范围内驱动它，审计中同时记录实际发消息的用户。管理员默认只读；被显式分享 `chat` 后按普通 `chat` 参与者处理。计划任务和 API token 同理。
- 审批请求沿会话树向上找第一个对该操作 allow 的 agent 会话（根会话的 agent 也算），都不 allow 或 agent 上交时交给根的所有者；被分享的用户不能审批。

## 操作者

每个任务、每条审计记录都记录操作者，以及其代表的用户：

| actor_type | actor_id | on_behalf_of |
|---|---|---|
| `user` | 用户 id | 用户本人 |
| `session` | 会话 id | 会话所有者 |
| `subagent` | 子会话 id | 父会话所有者 |
| `schedule` | 计划任务 id | 计划任务所有者 |
| `api_token` | token id | token 所属用户 |
| `system` | 组件名 | — |

权限检查一律从 `on_behalf_of` 用户开始：先检查这个用户能否访问目标节点，再沿规则链逐级判定，见下文"授权规则"。

## 授权规则

crhs 的授权规则决定"这个操作者能不能发起这个任务"。规则可以用 `privileged` 字段区分特权和普通任务（D86）：`native` / `ignore` 节点上，crhs 规则是特权任务唯一的关口。`forward` 节点上，特权任务能否执行最终由 crha 特权模式的信任配置决定（见 [privilege.md](privilege.md)），两者都要通过。

### 规则链

用户和组织**没有长期规则**。规则链的根是一个代表用户行事的对象：

| 场景 | 规则链 |
|---|---|
| WebUI 中手动执行 | 无：用户本人操作，只检查能否访问节点（管理员，或通过访问授权获得） |
| 会话 | 根会话 → 子会话 → …（每个 subagent 都是独立的会话） |
| MCP | API token |
| 计划任务 | 计划任务 → 会话（每次运行新建） → 子会话 → … |

- **根**（根会话、计划任务、API token）不直接写规则，由用户选择一个**规则预设**（`rule_sets.rule_preset`，API 字段 `rulePreset`；D116 前叫 preset），映射为实际规则：

  | 规则预设 | 映射为 |
  |---|---|
  | Ask | 放行非特权的读类操作（`file.read`，含 stat、列目录），其余（包括所有特权任务）`default = require-approval`，交给用户审批 |
  | Auto Review | 同 Ask，但审批先交给审查模型（模型预设"自动复核"）：判定安全则批准，有风险或不确定时交给用户 |
  | Yolo | `default = allow` |

  用户可以随时修改根的规则预设；审批时选择"以后都允许"，会在根上追加一条 `allow` 规则（方法 + 节点 + `exact` 或 `prefix`，预填为这次的目标，用户可以修改）。这些修改都记入审计。
- **子会话**由父会话（agent）用完整的规则配置创建，用于细粒度地限制 subagent，只能在上一级的基础上收紧。

### 规则

```json
{
  "default": "inherit",
  "rules": [
    { "action": "deny",             "method": "file.write", "nodes": ["prod"], "prefix": "/etc/crha/" },
    { "action": "allow",            "method": "exec", "nodes": ["web"], "prefix": "systemctl status " },
    { "action": "allow",            "method": "exec", "nodes": ["web-1"], "exact": "systemctl restart nginx" },
    { "action": "require-approval", "method": "exec" },
    { "action": "allow",            "method": "file.read" }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `action` | `allow` / `deny` / `require-approval` |
| `method` | `exec` / `file.read` / `file.write`，与 crha 相同；省略表示所有方法。stat、列目录属于 `file.read`，编辑属于 `file.write`。`allow file.write` 同时放行对同一目标的读；`deny` 和 `require-approval` 只匹配写本身，`deny file.write /etc/x` 不会连读也禁止 |
| `nodes` | 节点和节点组的列表，写名字或 UUID，保存时一律解析成 UUID（节点与节点组共用一个名字空间，见上文）；`_all` 原样保存，表示当前操作者可访问的所有节点，在使用时求值；省略等价于 `["_all"]`。改名不影响规则；引用的对象被删除后显示为"已删除的节点 / 节点组" |
| `privileged` | `true` 只匹配特权任务，`false` 只匹配普通任务；省略表示两者都匹配。"以后都允许"追加的规则带上这次任务的 `privileged` 值。M4 之前创建的规则由迁移设为 `false`，不会在升级后自动放行特权任务 |
| `exact` / `prefix` | 作用于目标（exec 为渲染后的 argv，文件操作为规范化后的路径，同 [privilege.md](privilege.md#方法与目标)）；`exact` 要求完全相等，`prefix` 要求前缀相等；省略表示任意目标。crhs 的规则**不支持 `regex`**：它在 crhs 的事件循环里执行，一个回溯严重的表达式就能卡住整个服务（crha 的信任规则用 RE2，不受影响） |
| `default` | 这一级没有规则命中时的结果。根：`allow` / `require-approval` / `deny`（由选项决定）；子会话：`inherit`（默认，不额外限制）/ `require-approval` / `deny` |

### 判定

规则是**逐级收紧的权限上限**：根确定初始权限，之后每一级只能在上一级的基础上进一步限制。

1. 先求每一级自己的结果 `r`：取这一级所有命中规则中**最严格**的一个（deny > require-approval > allow）；没有命中时取这一级的 `default`。
2. 再从根开始，逐级求**有效结果** `e`：`e₀ = r₀`；之后每一级 `eₖ = 最严格(eₖ₋₁, rₖ)`，其中 `inherit` 和 `allow` 都表示"不额外限制"。
3. 最后一级的有效结果就是最终结果：`allow` 放行，`deny` 拒绝，`require-approval` 按下文审批。

下级的 `allow` 不能放宽上级，只在配合 `default = "deny"` 或 `"require-approval"` 写白名单时有意义，例如"这个子会话默认拒绝，只放行 `systemctl status`"。

### 审批

- 审批结果是**工具调用本身的状态**：任务停在 `awaiting_approval`，决定（批准 / 拒绝、决定者、时间、理由、每一级的判断记录）保存在任务上；批量执行时保存在任务组上，一个任务组只审批一次。"以后都允许"另外修改规则，见上文。
- 规则链上的规则变化（用户改选项、追加规则）后，重新判定该链上所有还在等待的任务：变成 allow 就下发，变成 deny 就结束。
- 审批没有期限：一直等待，直到处理它的 agent 或根的所有者决定、规则变化使它不再需要审批，或者发起它的 API token 被吊销（等待项随之被拒绝）。
- 审批请求从发起操作的那一级开始逐级向上，根会话的 agent 和更下面的会话一样是普通的一级：
  - 某个祖先对这个操作的有效结果是 allow：请求交给它的 agent 判断，可以批准、拒绝，或者继续向上交（只会出现在限制是在更下面的级别加上的时候）。
  - 某个祖先的有效结果是 require-approval：跳过它，继续向上。
  - 没有 allow 的祖先，或者 agent 上交：规则预设为 Auto Review 时先交给审查模型（模型预设"自动复核"，见 [agent-runtime.md](agent-runtime.md#模型预设)；没有指定模型时，会话用自己的模型，计划任务用计划任务的模型）；最终由根的所有者在 WebUI 中审批。
- 处理请求的 agent 在自己的会话中做决定：前台 subagent 的等待会被打断并转入后台，父会话处理后再显式等待，见 [agent-runtime.md](agent-runtime.md#处理子会话的请求)。处理结果记入审计（actor 是处理它的会话），`escalate` 之后由用户在审批页决定。
- 等待项带 `root_session_id`（所属会话树）和 `handler_type` / `handler_session_id`（当前由哪个 agent 会话处理；由用户处理时是 `on_behalf_of_user_id`）。用户审批页只列 `handler_type = "user"` 的请求，agent 正在处理的请求在会话侧处理，不重复出现在用户页。
- 审批请求中始终展示完整的规则链和每一级的判断记录。节点只信任用户签名时，用户签名这一步同时也算作对 crhs 审批的批准，用户不需要操作两次。

### 配额

配额用来管理会话用量（防止循环、空跑、无人值守的运行失控），不是金额限制（见 [agent-runtime.md](agent-runtime.md#配额)）：

- `sessions.quota_tokens` 是有符号 64 位整数，表示剩余 token；任何一级都可以不设（`null` 不限，也不扣减）。用户创建的根会话默认不设；计划任务的会话在根上设为 `token_budget`；子会话由父会话给出。
- 每次模型调用（含压缩和 Auto Review）只计输出 token（上游不上报时按输出字节 × 0.3 估算），从该会话和链上每一个设了配额的级别（含根）扣减。这些级别都 > 0 才继续，否则下一次工具调用暂停。
- 暂停时会话的状态变为 `awaiting`，只向耗尽那一级的**直接上级**报告：子会话由父会话的 agent 增加 token（不按自身剩余封顶）或拒绝，父会话是根时由根会话的 agent 决定；根由所有者在审批页处理。拒绝或 abort 结束运行，会话置为 `idle`（状态定义见 agent-runtime.md "会话状态"）。
- 配额可以为负；设置配额是替换剩余量；不设用户级或组织级配额，也不计算货币成本。

## API Token

- 属于创建它的用户，有过期时间，可以随时吊销；只保存哈希。
- 是 MCP 规则链的根：创建时选择 Ask 或 Yolo（Auto Review 在 M3 之后可用），可以随时修改，也可以追加规则。能访问的节点与所属用户相同。
- 不能执行管理操作：管理员的 token 也不能管理用户、用户组和模型配置，也不能管理节点、节点组和访问授权。

## 扩展预留：OIDC

暂不实现，但现有设计不能阻塞它：

- 登录和用户身份分开：登录方式只负责得出"这是哪个用户"，之后的 Web 会话、权限判断与登录方式无关。`users.password_hash` 可以为空，OIDC 用户可以没有密码。
- 以后增加 `user_identities (user_id, provider, subject)` 表，把外部身份关联到本地用户；首次登录时自动创建普通用户，或者只允许关联到已有用户。
- 用户组以后可以从 OIDC 的 groups 声明同步，`user_groups` 预留 `source` 字段（`local` / 外部来源）。
- 提权签名与登录无关：OIDC 只用于登录 WebUI，签发授权仍然使用用户的 SSH key 或 Passkey。

## 审计

授权列表（WebUI 的授权页、`GET /api/authorizations`）只对管理员开放，列出整个组织的授权；普通用户可以提交授权，但看不到列表。

### 记录内容

| 类别 | 事件 |
|---|---|
| 认证 | 登录、登录失败、token 创建与吊销、凭证增删 |
| 节点 | 注册申请、确认、删除、上线、下线、访问授权的增删、信任配置变化（特权模式上报的配置摘要变化） |
| 任务 | 创建、策略结果、审批、下发、结束（含退出码和输出哈希）、unknown |
| 授权 | crhs 签发的授权与联署、用户授权的签发、本地批准（由特权模式上报） |
| Agent | 会话创建、工具调用（参数摘要）、模型调用元数据（模型、token 数、费用）、auto review 结论 |
| 用户 | 用户与用户组的增删改、用户类型变化、会话的分享与取消分享 |
| 配置 | 授权规则、计划任务、模型配置的修改 |

会话的完整记录在 durable 的表中，审计只记录元数据和引用，不重复存储内容。

### 防篡改

- 审计只追加写入，不带哈希链。数据库使用单一应用账号（D61），能改库的人也能改写任何库内校验，所以库内不做防篡改；需要防篡改时把审计外送到 crhs 之外的信任域（syslog、webhook，后续）。超过保留期的审计记录会被删除，见 [data-model.md#保留期](data-model.md#保留期)。
- 节点：crha 特权模式写本地日志并同时写入 journald。crhs 即使被攻破，也无法删改节点上特权任务的执行记录（主机内的篡改暂不在威胁模型内）。
- 外送（后续）：syslog、webhook，用于把审计同步到另一个信任域。

## 迁移

从"节点属于用户 + 节点分享 + 组成员关系由 crha 定义"迁移到本设计：

- 节点：删除所有者。原所有者不是管理员时，为其创建一条该节点的访问授权。
- 节点分享：`operate` 转为访问授权；`view` 直接删除。迁移写一条审计记录说明转换和删除的数量。
- 节点组：用迁移前 `node_groups` 缓存中的组名（crha 上报的和 SSH 节点维护的）创建节点组并设置成员。
- 名字：不合规的节点名和节点组名按上文规则改名；节点与节点组重名时节点组加后缀。
- 规则：`rule_sets` 中的 `group:x` 改成节点组 UUID，节点名或 id 改成节点 UUID；无法解析的保留为"已删除"引用。
- 已签发的、`nodes` 里含 `group:` 的可复用授权会被新 crha 拒绝；它们都带 `deadline`，到期自然失效，不改写。
- 节点上的 `privileged.toml` 需要人工把 `groups` 换成 `aliases`（UUID 由 WebUI 显示）；`crha.toml` 中的 `groups` 直接删除（非特权模式没有别名）。
