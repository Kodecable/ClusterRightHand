# 用户、归属与审计

## 用户模型

单组织、多用户。所有表都带 `org_id`，但 v1 只有一个组织，不提供多组织功能。

| 对象 | 说明 |
|---|---|
| User | 登录 WebUI 的人，分为**管理员**和**普通用户**两种。v1 用本地密码 + Passkey 登录 |
| UserGroup | 用户组，由管理员维护，用于分享 |
| UserCredential | 用户的签名凭证：SSH 公钥（含 FIDO 硬件 key）、Passkey。用于登录和签发提权授权 |
| ApiToken | 属于某个用户，作为操作者链上的一级，只能收紧；MCP 和自动化使用 |
| Node | 节点，属于一个用户，可以属于多个（节点）组 |
| Group | 节点组，例如 `web`、`prod`。用于选择节点（授权规则、批量执行、计划任务），也是 crha 特权模式的授权单位 |

"组"单独出现时指节点组，用户的组一律称为"用户组"。

节点用**组**来组织，不另设标签。凡是需要"一组节点"的地方，都写成节点和组的列表，例如 `["web-1", "group:prod"]`。

组成员关系**只在 crha 侧定义**，crhs 侧的组数据只是缓存：

- 节点在连接时通过 `Facts` 上报自己所属的组，配置变化（reload）后主动推送，crhs 据此刷新缓存。
- 组定义在 crha 的本地配置中：使用特权模式（`forward`）时以 `privileged.toml` 的 `groups` 为准，它同时也是授权依据（发给某个组的授权，特权模式只在本机配置了这个组时才认为是发给自己的，见 [privilege.md](privilege.md#授权)）；不使用特权模式时在 `crha.toml` 中定义。
- 调整节点的组，就是修改 crha 配置并 reload，和其他配置修改一样是普通的特权任务。
- SSH 节点没有 crha，它的组在 crhs 中直接维护。
- 组名是全局的，`group:web` 匹配所有上报了 `web` 的节点，但一个用户只能选中自己**能访问**的那部分（见下文"归属与分享"）。

## 用户类型

不设角色和细粒度权限，只有两种用户：

| 类型 | 能做什么 |
|---|---|
| 管理员 | 普通用户的全部能力；管理用户和用户组；模型配置；查看所有节点和会话（别人的会话只读，不能代替所有者发消息或改规则，但可以管理分享）；查看全部审计；转移资源的归属 |
| 普通用户 | 管理自己的节点、会话、计划任务、API token；访问分享给自己的节点和会话；查看与自己相关的审计 |

"能对节点做什么"不由权限表决定：用户本人操作时只看"能否访问这个节点"；代表用户行事的会话、计划任务和 API token 还要受自己规则链上的授权规则约束（见下文）。

在只信任用户的节点上，crhs 侧的任何身份都不足以提权，必须由该节点信任数组中的用户本人签名（或在节点上本地批准），见 [privilege.md](privilege.md)。

## 归属与分享

节点和会话都**明确属于一个用户**：

- 节点属于创建注册令牌（或添加 SSH 节点）的用户。
- 会话属于创建它的用户；subagent 的子会话、计划任务产生的会话，属于父会话或计划任务的所有者。
- 计划任务和 API token 也属于创建者，但不支持分享。

节点和会话都可以**分享**给额外的用户或用户组：

| 资源 | 访问级别 | 含义 |
|---|---|---|
| 节点 | `view` | 查看节点、Facts、任务和输出 |
| 节点 | `operate` | 在 `view` 之外，对节点执行任务（包括请求特权任务）；通过自己的会话或 token 执行时，受它们的授权规则约束 |
| 会话 | `view` | 查看会话内容和状态 |
| 会话 | `chat` | 在 `view` 之外，向会话发送消息、打断运行 |

- 分享、取消分享、删除只能由所有者（或管理员）操作；转移归属只能由管理员操作。
- 分享根会话也覆盖它下面的 subagent 子会话；子会话也可以单独分享。继承来的 `view` / `chat` 取链上最强的一级。撤销分享会关闭该会话（或覆盖它的根会话）上已经建立的事件流。
- 一个用户能访问的节点 = 自己的节点 + 分享给自己（或自己所在用户组）的节点；管理员可以访问所有节点。
- **会话以所有者的身份行事**：被分享了 `chat` 的用户向会话发消息时，能访问的节点是所有者的，规则是这个会话自己的。分享会话等于让对方在所有者授予会话的范围内驱动它，审计中同时记录实际发消息的用户。
- 审批请求到达链顶端时交给根的所有者，被分享的用户不能审批。
- 分享节点时不附带额外的规则。如果节点只信任所有者的签名，其他用户的特权任务自然需要所有者签名。

## 操作者

每个任务、每条审计记录都记录操作者，以及其代表的用户：

| actor_type | actor_id | on_behalf_of |
|---|---|---|
| `user` | 用户 id | 用户本人 |
| `session` | 会话 id | 会话所有者 |
| `subagent` | 子会话 id | 父会话所有者 |
| `schedule` | 计划任务 id | 计划任务所有者 |
| `api_token` | token id | token 所属用户 |
| `system` | 组件名 | — |

权限检查一律从 `on_behalf_of` 用户开始：先检查这个用户能否访问目标节点，再沿规则链逐级判定，见下文"授权规则"。

## 授权规则

crhs 的授权规则决定"这个操作者能不能发起这个任务"，与特权**解耦**：规则不区分特权和普通任务，特权任务能否在节点上执行只由 crha 特权模式的信任配置决定（见 [privilege.md](privilege.md)）。特权任务两者都要通过。

### 规则链

用户和组织**没有长期规则**。规则链的根是一个代表用户行事的对象：

| 场景 | 规则链 |
|---|---|
| WebUI 中手动执行 | 无：用户本人操作，只检查能否访问节点（自己的节点，或被分享了 `operate`） |
| 会话 | 根会话 → 子会话 → …（每个 subagent 都是独立的会话） |
| MCP | API token |
| 计划任务 | 计划任务 → 会话（agent 类型） |

- **根**（根会话、计划任务、API token）不直接写规则，由用户选择一个选项，映射为实际规则：

  | 选项 | 映射为 |
  |---|---|
  | Ask | 放行读类操作（`file.read`，含 stat、列目录），其余 `default = require-approval`，交给用户审批 |
  | Auto Review | 同 Ask，但审批先交给审查模型：判定安全则批准，有风险或不确定时交给用户（需要配置模型，M3） |
  | Yolo | `default = allow` |

  用户可以随时修改根的选项；审批时选择"以后都允许"，会在根上追加一条 `allow` 规则（方法 + 节点 + `exact` 或 `prefix`，预填为这次的目标，用户可以修改）。这些修改都记入审计。
- **子会话**由父会话（agent）用完整的规则配置创建，用于细粒度地限制 subagent，只能在上一级的基础上收紧。

### 规则

```json
{
  "default": "inherit",
  "rules": [
    { "action": "deny",             "method": "file.write", "nodes": ["group:prod"], "prefix": "/etc/crha/" },
    { "action": "allow",            "method": "exec", "nodes": ["group:web"], "prefix": "systemctl status " },
    { "action": "allow",            "method": "exec", "nodes": ["web-1"], "exact": "systemctl restart nginx" },
    { "action": "require-approval", "method": "exec" },
    { "action": "allow",            "method": "file.read" }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `action` | `allow` / `deny` / `require-approval` |
| `method` | `exec` / `file.read` / `file.write`，与 crha 相同；省略表示所有方法。stat、列目录属于 `file.read`，编辑属于 `file.write`。`allow file.write` 同时放行对同一目标的读；`deny` 和 `require-approval` 只匹配写本身，`deny file.write /etc/x` 不会连读也禁止 |
| `nodes` | 节点和组的列表；省略表示所有节点 |
| `exact` / `prefix` | 作用于目标（exec 为渲染后的 argv，文件操作为规范化后的路径，同 [privilege.md](privilege.md#方法与目标)）；`exact` 要求完全相等，`prefix` 要求前缀相等；省略表示任意目标。crhs 的规则**不支持 `regex`**：它在 crhs 的事件循环里执行，一个回溯严重的表达式就能卡住整个服务（crha 的信任规则用 RE2，不受影响） |
| `default` | 这一级没有规则命中时的结果。根：`allow` / `require-approval` / `deny`（由选项决定）；子会话：`inherit`（默认，不额外限制）/ `require-approval` / `deny` |

### 判定

规则是**逐级收紧的权限上限**：根确定初始权限，之后每一级只能在上一级的基础上进一步限制。

1. 先求每一级自己的结果 `r`：取这一级所有命中规则中**最严格**的一个（deny > require-approval > allow）；没有命中时取这一级的 `default`。
2. 再从根开始，逐级求**有效结果** `e`：`e₀ = r₀`；之后每一级 `eₖ = 最严格(eₖ₋₁, rₖ)`，其中 `inherit` 和 `allow` 都表示"不额外限制"。
3. 最后一级的有效结果就是最终结果：`allow` 放行，`deny` 拒绝，`require-approval` 按下文审批。

下级的 `allow` 不能放宽上级，只在配合 `default = "deny"` 或 `"require-approval"` 写白名单时有意义，例如"这个子会话默认拒绝，只放行 `systemctl status`"。

### 审批

- 审批结果是**工具调用本身的状态**：任务停在 `awaiting_approval`，决定（批准 / 拒绝、决定者、时间、理由、每一级的判断记录）保存在任务上；批量执行时保存在任务组上，一个任务组只审批一次。"以后都允许"另外修改规则，见上文。
- 规则链上的规则变化（用户改选项、追加规则）后，重新判定该链上所有还在等待的任务：变成 allow 就下发，变成 deny 就结束。
- 审批没有期限：一直等待，直到根的所有者决定、规则变化使它不再需要审批，或者发起它的 API token 被吊销（等待项随之被拒绝）。
- 审批请求从发起操作的那一级开始逐级向上：
  - 上一级对这个操作的有效结果是 allow，且它是一个 agent 会话：由它的 agent 判断，可以批准、拒绝，或者继续向上交（只会出现在限制是在更下面的级别加上的时候）。
  - 上一级的有效结果是 require-approval：直接继续向上交。
  - 到达根：选项为 Auto Review 时先交给审查模型；最终由根的所有者在 WebUI 中审批。
- 上一级 agent 在自己的会话中处理请求：前台 subagent 的等待会被打断并转入后台，父会话处理后再显式等待，见 [agent-runtime.md](agent-runtime.md#处理子会话的请求)。处理结果记入审计（actor 是父会话），`escalate` 之后由用户在审批页决定。
- 等待项带 `root_session_id`（所属会话树）和 `handler_type` / `handler_session_id`（当前由哪个 agent 会话处理；由用户处理时是 `on_behalf_of_user_id`）。用户审批页只列 `handler_type = "user"` 的请求，agent 正在处理的请求在会话侧处理，不重复出现在用户页。
- 审批请求中始终展示完整的规则链和每一级的判断记录。节点只信任用户签名时，用户签名这一步同时也算作对 crhs 审批的批准，用户不需要操作两次。

### 配额

配额只用于 subagent，用来管理子会话（防止循环、空跑），不是金额限制（见 [agent-runtime.md](agent-runtime.md#配额)）：

- `sessions.quota_tokens` 是有符号 64 位整数，表示剩余 token；子会话可以不给（`null` 不限）；根会话固定为 0，且从不扣减。
- 每次模型响应后从该会话和链上每一个 subagent 级别扣减；根不扣。所有 subagent 级别都 > 0 才继续，否则下一次工具调用暂停。
- 暂停时子会话的状态变为 `awaiting`，只向**直接父会话**报告；父会话的 agent 增加 token（不按自身剩余封顶）或拒绝；拒绝或 abort 把子会话置为 `stopped`；父会话是根时由根会话的 agent 决定。
- 配额可以为负；设置子会话配额是替换剩余量；不设用户级或组织级配额，也不计算货币成本。

## API Token

- 属于创建它的用户，有过期时间，可以随时吊销；只保存哈希。
- 是 MCP 规则链的根：创建时选择 Ask 或 Yolo（Auto Review 在 M3 之后可用），可以随时修改，也可以追加规则。能访问的节点与所属用户相同。
- 不能执行管理操作：管理员的 token 也不能管理用户、用户组和模型配置，也不能转移归属。

## 扩展预留：OIDC

暂不实现，但现有设计不能阻塞它：

- 登录和用户身份分开：登录方式只负责得出"这是哪个用户"，之后的 Web 会话、权限判断与登录方式无关。`users.password_hash` 可以为空，OIDC 用户可以没有密码。
- 以后增加 `user_identities (user_id, provider, subject)` 表，把外部身份关联到本地用户；首次登录时自动创建普通用户，或者只允许关联到已有用户。
- 用户组以后可以从 OIDC 的 groups 声明同步，`user_groups` 预留 `source` 字段（`local` / 外部来源）。
- 提权签名与登录无关：OIDC 只用于登录 WebUI，签发授权仍然使用用户的 SSH key 或 Passkey。

## 审计

### 记录内容

| 类别 | 事件 |
|---|---|
| 认证 | 登录、登录失败、token 创建与吊销、凭证增删 |
| 节点 | 注册申请、确认、删除、上线、下线、分享与取消分享、归属转移、信任配置变化（特权模式上报的配置摘要变化） |
| 任务 | 创建、策略结果、审批、下发、结束（含退出码和输出哈希）、unknown |
| 授权 | crhs 签发的授权与联署、用户授权的签发与吊销、本地批准（由特权模式上报） |
| Agent | 会话创建、工具调用（参数摘要）、模型调用元数据（模型、token 数、费用）、auto review 结论 |
| 用户 | 用户与用户组的增删改、用户类型变化、会话的分享与取消分享 |
| 配置 | 授权规则、计划任务、模型配置的修改 |

会话的完整记录在 durable 的表中，审计只记录元数据和引用，不重复存储内容。

### 防篡改

- 服务端：`audit_events` 每条记录包含 `prev_hash` 和 `hash = SHA-256(prev_hash || 规范化后的记录)`，形成哈希链。
- 数据库只用一个应用账号，它拥有迁移、安装和正常运行所需的全部权限，不另设只读或只追加的账号。因此哈希链只能**发现**绕过 crhs 的改动（直接改库、删掉中间的记录），挡不住已经被攻破、能重算整条链的 crhs；要防这种情况，需要把链头定期送到另一个信任域（见下文"外送"）。
- 节点：crha 特权模式写本地日志并同时写入 journald。crhs 即使被攻破，也无法删改节点上特权任务的执行记录（主机内的篡改暂不在威胁模型内）。
- 外送（后续）：syslog、webhook，用于把审计同步到另一个信任域。
