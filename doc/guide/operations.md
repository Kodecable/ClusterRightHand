# Operations

Installation is covered in [Install](install.md).

## Service management

A deployment has one crhs process and, on each crha node, the crha unprivileged mode plus, in `forward`
mode, the privileged mode. The units are generated by `crhs init` and `crha enroll`
([Run as a service](install.md#run-as-a-service)).

| Process | Stop | Reload |
|---|---|---|
| crhs | `SIGTERM`; it finishes in-flight work for up to 10 seconds | None; restart it |
| `crha run` | `SIGTERM` | `SIGHUP` re-reads `crha.toml` |
| `crha privileged run` | `SIGTERM` | `SIGHUP` re-reads `privileged.toml` |

Do not send `SIGHUP` to crhs; it terminates the process.

Run one crhs process per database. crhs keeps connections and scheduling state in memory, so a second
process on the same database is not supported.

## Reloading configuration

Each process reloads only its own file. An invalid file is not applied; the process keeps running with
the old configuration and logs the error.

- `crha run` applies changes to `server`, `tls_verify` and `notes` on reload. Other settings, such as
  `state_dir`, `[output]` and `[privileged]`, need a restart, and crha logs which ones.
- `crha privileged run` applies trust entries, aliases, guard rules and `clock_skew` on reload, and
  reports the new trust configuration to crhs. The socket, state directory and log path need a restart.

```sh
sudo systemctl reload crha
sudo systemctl reload crha-privileged
```

Changing `privileged.toml` through CRH is a privileged task (a file write followed by a reload), and
needs an authorization from a signer the node already trusts.

## Upgrades

Upgrade crhs first, then its crha nodes. A node with a different protocol minor version is
compatible. A node of a protocol major crhs does not serve is refused when it connects (crha logs
`crhs does not serve protocol major` with the majors crhs serves) and is upgraded by hand; each
release's notes say which majors it serves.

Back up the database and take a key export first ([Backups and restore](#backups-and-restore)). Migrations
run automatically when crhs starts and cannot be reversed, so the database backup is the rollback.

**crhs, tar with Node.** Unpack the new archive and run its `install.sh`. The version is installed next
to the old one under `/opt/crhs/versions`, and `/opt/crhs/current` switches to it. Then:

```sh
sudo systemctl restart crhs
```

Keep the previous version directory to switch back with `ln -sfn`. Switch back only together with the
database backup taken before the upgrade: the newer database was migrated for the newer crhs.

**crhs, container.** Pull the new image and recreate the container with the same volume:

```sh
sudo podman pull ghcr.io/kodecable/crhs:<version>
sudo podman rm -f crhs
sudo podman run -d --name crhs -p 8080:8080 -v /srv/crhs:/crhs-data ghcr.io/kodecable/crhs:<version>
```

**crhs, tar without Node.** Replace the directory with the new bundle, run `npm ci --omit=dev` in it,
then `sudo systemctl restart crhs`.

**crha, from crhs.** On a node's page or a node group's page, **Upgrade crha** brings crha to crhs's own
version; `POST /api/nodes/upgrade` does the same. It first shows which nodes are upgraded, how many
running tasks the restart will end, and which nodes are skipped and why. crhs then fetches the crha
release of its version, verifies it, and starts one privileged task group per architecture, which waits
for an authorization like any privileged task; when signing, compare the binary's hash with the line
`crha-<version>-linux-<arch>/crha` of the release's `SHA256SUMS`, for example with `crhu sign --spec …
--content crha-<version>-linux-<arch>/crha`. A crhs built from a commit rather than
a release cannot upgrade nodes. On each node the new binary checks the configuration,
backs up and regenerates the units, restarts crha, and rolls back by itself when the new version does
not come up within two minutes ([crha self-upgrade](../design/distribution.md#crha-self-upgrade)). If
that rollback fails too, or the installer was killed halfway, the node accepts no further upgrade until
`sudo crha upgrade rollback` has undone it; `crha upgrade status` says so.

- Only nodes set up with `crha enroll`, running under systemd, not installed from a deb or rpm, and
  with a privileged side that runs as root can be upgraded this way. An `ignore` node qualifies when
  crha itself runs as root: enroll runs it as the crha user, so add a drop-in with
  `sudo systemctl edit crha` (`[Service]`, `User=root`, `Group=root`); upgrades rewrite the unit but
  keep drop-ins. The node page says why a node cannot be upgraded.
- crhs needs to reach GitHub and the Sigstore TUF repository. Without them, set
  `[crha_release] verify = false` and copy the release archive to `crha-releases/<version>/` under the
  data directory ([crha_release](reference/crhs-config.md#crha_release)).
- An upgrade may change how the node behaves: a release can turn a default off for safety, or rename
  or drop a configuration key, and migrates the files itself. Read the release notes before upgrading;
  the upgrade log lists every change made to `crha.toml` and `privileged.toml`, and the backup keeps
  the previous files.
- `crha upgrade status` on the node prints the last upgrade's outcome and the upgrade log, which crhs
  can also read with the node's file view. If the new version starts but cannot reach crhs,
  `sudo crha upgrade rollback` goes back to the version before it; it refuses when a file changed since
  the upgrade, unless `--force`.

**crha, deb and rpm.** Install the new package; the package restarts `crha-privileged` and then `crha`.
The rpm signing key must already be imported ([deb and rpm](install.md#deb-and-rpm)):

```sh
sudo apt install ./crha_<version>_<arch>.deb
sudo dnf install ./crha-<version>-1.<rpmarch>.rpm
```

**crha, tar.** Run the new archive's `install.sh`, then restart the privileged mode before the agent:

```sh
sudo systemctl restart crha-privileged
sudo systemctl restart crha
```

If you upgrade by hand through a CRH task, schedule the restart after the task reports (for example
`systemd-run --on-active=2s systemctl restart crha`), because a restart ends every running task,
including the one doing the upgrade. **Upgrade crha** handles this itself.

**Effect on running work.** After a crhs restart, crha nodes reconnect and their running tasks continue;
tasks on SSH nodes become `unknown`. After a crha restart, the tasks that were running on that node
become `unknown`.

## Backups and restore

Back up three things:

| Item | Why |
|---|---|
| The database | All crhs data, including secrets in encrypted form |
| The master key file (`master_key_file`) | Decrypts the secrets |
| A key export (`crhs keys export`) | A passphrase-protected copy of the master key and crhs's own keys |

The database and the master key belong together; neither is useful alone. The database and the library
storage (the `library/` directory under the data directory, or the WebDAV collection when the `webdav`
backend is used) must be backed up together, since files are only identifiable through the database.

**SQLite.** Stop crhs and copy the database file together with its `-wal` and `-shm` files, or back it up
online:

```sh
sqlite3 /var/lib/crhs/crhs.db ".backup '/backup/crhs-$(date +%F).db'"
```

Copying only the database file while crhs runs can miss recent transactions.

**PostgreSQL.**

```sh
pg_dump --format=custom --no-owner --file /backup/crhs-$(date +%F).dump "$DATABASE_URL"
```

**Key export.** Run it once after the first start of crhs, which creates crhs's keys:

```sh
sudo -u crhs crhs keys export --out /var/lib/crhs/crhs-keys.age --config /etc/crhs/crhs.toml
```

It asks for a passphrase and writes an [age](https://age-encryption.org/) file, which the standard `age`
tool can also decrypt. The file contains crhs's private keys: store it offline, apart from the database
backups. Node keys are not included; a node that loses its key re-enrolls with a Re-enroll token, which
keeps its record.

**Restore:**

1. Stop crhs.
2. Restore the database.
3. Put the master key file back (mode 0600, owned by the crhs user), or recreate it from the export:

   ```sh
   sudo -u crhs crhs keys import /var/lib/crhs/restore.age --config /etc/crhs/crhs.toml
   ```

   `keys import` checks that the export belongs to the restored database and refuses to overwrite an
   existing key file.
4. Start crhs, sign in, and check that nodes reconnect and recent data is present.

If you start from an empty database instead, crhs creates new keys. Every node must then enroll again,
and every `privileged.toml` that trusts the old crhs signing key must be updated.

Test a restore on a spare host before you need one.

## Logs

crhs logs to standard output and standard error, crha to standard error; under systemd, read them with
`journalctl -u crhs`, `journalctl -u crha` and `journalctl -u crha-privileged`.

- crhs logs its listen address and key fingerprints at startup, then warnings and errors. It does not
  log requests; use the audit log in the WebUI to see who did what.
- crha writes one human-readable line per record. On a terminal it starts with the local time and a
  level word (`2026-11-23 10:04:05.123 INFO  crha starting ...`); when stderr is the journal's stream,
  journald supplies the time and the line carries only the priority prefix and the message
  (`<6>crha starting ...`). Fields follow the message as `key=value`, with values quoted when they
  contain spaces, `=` or quotes. A relayed native helper record keeps the task's full `spec=` as raw
  JSON ([native mode](../design/privilege.md#native-mode)); there it is the only record of what ran
  privileged.
- crha logs its connection, reloads and errors. A node that crhs rejects exits with the reason.
- The privileged mode also writes every accepted and refused task to the JSON-lines file named by `log`
  in `privileged.toml`, the durable copy with the time and the full task specification. It does not
  rotate the file; use `logrotate` with `copytruncate`. The same records are mirrored to the journal
  as the human-readable lines above, without the time and without the full specification.

## Retention and cleanup

The retention windows in the WebUI's **System settings** (administrators) set how long finished tasks,
audit events and finished agent tool records are kept (90, 180 and 7 days by default; `"off"` keeps
them forever; the minimum is one day). A change applies to the next sweep; see the
[crhs configuration reference](reference/crhs-config.md#system-settings). Tasks still in progress are
never deleted, and the most recent audit events are always kept.

Session conversations are never deleted by retention. They grow with use, so size the database for
them.

On nodes, crha deletes complete task output files after `[output].max_age` (7 days) or when they exceed
`[output].max_total` (1 GiB).

## Rotating and revoking node keys

**Revoke a node:** delete it on its page in the WebUI. Its key stops working at once. Tasks waiting for
it fail; tasks running on it become `unknown`. Deleting a node also invalidates any re-enrollment token
issued for it.

**Replace a node's key** by re-enrolling it. The node keeps its id, name, node groups, access grants and
task history; there is no online rotation.

1. On the node's page, choose **Re-enroll** and copy the crhs address and token.
2. Run `sudo crha enroll` and answer yes to enrolling again with a new key. It stops the services,
   registers the new key, keeps the old one as `.old` files ([crha enroll](reference/cli.md#crha)) and
   starts the services again. With a manual layout, stop the services yourself and run
   `printf '%s\n' "$TOKEN" | crha register --replace --config /etc/crha/crha.toml`.
3. Approve the new key fingerprint in the WebUI after comparing it with `crha status`.

The old key stops authenticating as soon as the node enrolls, and its existing connection is closed.
`node_id` and `aliases` in `privileged.toml` still refer to the same node. If the host itself is no
longer trustworthy, revoke it by deleting the node instead.

Enrolling with a **New node** token instead registers another node: it starts without the old one's
name, groups and grants. `crha enroll` says so, points `node_id` in `privileged.toml` to the new id, and
leaves the previous node on crhs; delete it on its page once it is no longer needed.

**crhs's identity key** cannot be rotated online: every node pins it at enrollment, so replacing it
means re-enrolling every node with a Re-enroll token, which keeps their records. Back the key up with a
key export.

**crhs's authorization signing key** can be rotated while crhs runs. Add a key, add its public key to
each node's `privileged.toml` and reload the node when convenient, then delete the old key once no node
trusts it. crhs uses the newest key each node trusts, so nodes may be updated one at a time. Deleting a
compromised key stops crhs signing with it at once, but a node that still lists it continues to trust it;
remove the entry there as well. With no keys left crhs signs nothing and falls back to the owner's
signature or a local approval window.

## Clock synchronization

Run time synchronization (chrony, systemd-timesyncd) on the crhs host and every node. Nodes check
authorization deadlines with their own clock, so a wrong clock causes refusals or lets authorizations
last longer than intended.

A **clock** warning next to a node means its clock differed from crhs's by more than `clock_warn` in
**System settings** when it connected. Fix the clock, then restart `crha` so the offset is measured
again. The warning never blocks work. It is unrelated to `clock_skew` in `privileged.toml`, which is
the tolerance for checking authorizations; do not raise `clock_skew` instead of fixing the clock.

## SQLite and PostgreSQL

Choose before installing; there is no migration between the two.

| | SQLite | PostgreSQL |
|---|---|---|
| Best for | One machine, a small team, trials | Team deployments and long conversation histories |
| Setup | A file path | A server, a role and a database (version 14 or newer recommended) |
| Durability | A power loss can drop the last few transactions | Full |
| Session search | Titles only | Titles and message text |
| Backup | Stop and copy, or `sqlite3 .backup` | `pg_dump` |

## Troubleshooting

### A node is offline

Tasks for an offline crha node wait up to 30 seconds and then fail with `node_offline`; they are not
queued. Check:

1. `systemctl status crha` and `journalctl -u crha`. A rejection reason in the log means crhs refused
   the node.
2. `crha status --config /etc/crha/crha.toml` for the server URL and keys.
3. The node page in the WebUI: pending approval, or a trust warning.
4. The network path and the reverse proxy. A proxy that does not pass WebSocket upgrades on `/agent`
   leaves nodes offline while the WebUI works.

SSH nodes have no standing connection. Use **Test connection** on the node page and check that crhs can
reach every hop.

### Login is rate-limited or the captcha fails

- `rate_limited`: 10 failed logins from one address in 15 minutes. The limit resets after 15 minutes or
  when crhs restarts.
- `login_in_progress`: another login from the same address is in progress; retry.
- `captcha_failed`: the challenge expired (after two minutes) or the client address changed between
  challenge and login. Behind a proxy, set `real_ip_header` in **System settings** and make the proxy
  overwrite that header.
- `hash_busy`: too many password checks at once; retry, or raise `auth.argon2_concurrency` in
  **System settings**.
- If you are returned to the sign-in page right after signing in, the browser did not keep the session
  cookie: on any host other than localhost the WebUI must be served over HTTPS.

### A task waits for an authorization

The rules allowed the task, but a `forward` node needs a signature or an open local approval window. You can:

- sign with a Passkey on the task page or the Approvals page;
- sign with an SSH key on your workstation, then paste the result into the WebUI:

  ```sh
  crhu sign --payload '<payload from the WebUI>' --key ~/.ssh/id_ed25519
  ```

- open the window on the node, if your uid is in a `local` trust entry:
  `sudo crha approve --for 30m`. While it is open, crhs can run any privileged task on that node, and
  every privileged task already waiting there runs at once, whoever started it. Close it with
  `sudo crha lock` when done.

The wait expires after 24 hours. If nobody can authorize the command, crhs refuses the task with the
last code and message the node gave; check the node's trust panel. `alias_missing` means a group
authorization was used for a node whose `aliases` lack that group. `privileged_unavailable` means the
node's privileged mode is not running or has not reported its trust configuration.

### A task ended as unknown

crhs lost track of the task: the connection dropped (`connection_lost`), crha restarted
(`executor_restarted`), or the node never confirmed it received the task (`dispatch_unconfirmed`). The
command may or may not have run. Check the node before running it again; CRH never retries
automatically.

### A node stays pending

An enrolled node receives no tasks until an administrator approves it. Approve it in the WebUI after
comparing the fingerprint with `crha status`. A rejected node must enroll again.
